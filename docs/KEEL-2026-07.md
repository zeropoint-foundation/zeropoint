## Part II — Invariants (Layer A)

Compiled runtime commitments. Structural. Non-amendable except by shipping a new substrate binary through the release chain, which the community independently verifies.

### II.1 Cryptographic primitives

- Ed25519 for signing and verification.
- Blake3 for content hashing and chain linkage.
- HKDF-SHA256 for key derivation from Genesis.
- XChaCha20-Poly1305 for AEAD.
- HPKE (RFC 9180) with X25519 + HKDF-SHA256 + XChaCha20-Poly1305 for envelope encryption.
- Argon2id for password-based derivation (parameters per ENCRYPTED-STORAGE §11.3).

### II.2 Chain integrity

- Every receipt has the wire fields specified in whitepaper §4.1: id, rt, st, tg, ch, ts, pr, pd, ra, sg, ex.
- The chain is append-only, hash-linked via the pr field.
- Blake3 hash of receipt content produces ch.
- Ed25519 signature over the signable structure produces sg.
- Chain acceptance requires: every pr linkage intact, every ch consistent, every sg valid.
- Any modification propagates as hash failure detected by every subsequent verifier.
- Chain compaction via epoch seals (8,192 entries or 7 days) per whitepaper §4.5.

### II.3 Constitutional rules

- HarmPrincipleRule and SovereigntyRule evaluate at fixed positions 1 and 2 in the gate policy engine.
- Cannot be bypassed by capability grants, policy configuration, WASM modules, canonical spec amendments, or consensus votes.
- Attempts to remove or bypass either rule are themselves blocked by the SovereigntyRule.
- Applied to every action equally — operator-initiated, cognitive-layer inference-driven, third-party service calls under grant.

### II.4 Delegation narrowing

- Delegation chains verify against the eight invariants specified in whitepaper §5.2.
- Any violation rejects the entire chain.
- Narrowing is structural: at no hop can authority widen.

### II.5 Genesis-as-single-root (Decision A)

- Every sovereign has exactly one Genesis keypair as the single root of trust.
- Genesis is ultimately controlled by one or more humans; whether single or M-of-N is up to the sovereign at ceremony time.
- All other keys derive from Genesis by HKDF derivation (for keys that live in the operator's own signing/vault/CEK hierarchy) or by Genesis-certification via provisioning receipt (for hardware-backed keys of officers and devices).
- No non-Genesis root is a valid trust root.

### II.6 Officer signing keys

- Officers hold their own hardware-backed keys, locally generated on the substrate host's hardware, Genesis-certified via provisioning receipt.
- Officer signing is host-mediated: the host holds the key handle and exposes a sign() interface to the officer's WASM core.
- Officer findings are host-validated against the receipt schema and signed on emission — WASM cores cannot emit unsigned findings, cannot access private key material, cannot bypass schema validation.

### II.7 Cartographer as infrastructure

- The Cartographer holds no independent signing key.
- Cartographer state changes are local cache updates, not chain events.
- Operator-initiated ontology corrections are operator-signed; auto-corrections are unsigned local events.
- Ontology is a projection of the chain — deletable, rebuildable, disposable.

### II.8 Gate atomicity

- Every side-effecting action passes through the gate.
- No code path in the compiled substrate skips gate evaluation.
- Constitutional rules evaluate first, atomically, on every gated action.
- WASM modules cannot bypass — they access side-effect primitives only through host-mediated interfaces that gate-check on the way out.

### II.9 Two-layer architecture

- Layer A is compiled Rust; not amendable via canonicalization.
- Layer B is chain-anchored spec (WASM modules + canonical data records); amendable via canonicalization ceremony.
- The runtime rejects any Layer B spec that would violate Layer A. No override, no ceremony bypass.

### II.10 Composition contracts

- Officer trait — every officer WASM module must expose: awake(context), process(signals) → Vec<Finding>, finding_shape() → Schema. Import declarations for chain-reader, ontology-reader, charter-config-reader, sign-request. Deterministic execution constraint.
- Cartographer trait — analogous but without sign-request; adds ontology-writer for local cache.
- Regent trait — cognitive-cycle interface with operator input, chain reading, officer findings, delegation state, ontology state.
- WASM runtime enforces sandbox and resource metering.
- Traits are compiled into the substrate binary. Trait amendments require substrate re-ship.

### II.11 Canonicalization ceremony machinery

- Canonicalization receipt: chain-anchored, operator-signed, references artifact content hashes (WASM module Blake3 hashes, canonical data record hashes).
- Substrate observes canonicalization receipts on chain, fetches artifacts by hash, verifies signatures back to Genesis, verifies WASM against trait interfaces, loads or reloads.
- Ceremony rigor tiers structurally enforced:
  - Tier 1 (parameter adjustment within declared bounds) — single operator signature, immediate effect.
  - Tier 2 (WASM module swap or significant structured-data change) — ZEP proposal, single operator signature, immediate effect.
  - Tier 3 (component identity change, threshold change) — multi-signature from all provisioned sovereign devices, 14-day cooling period, active final confirmation.
  - Tier 4 (would cross Layer A boundary) — rejected structurally by substrate binary.

### II.12 Peer-to-peer messaging as core substrate

- Reticulum-compatible mesh transport ships in the substrate binary.
- LXMF-compatible messaging protocol (or ZP-native equivalent) ships.
- Session cryptography (attendance manifests, group DH, ephemeral keys, forward secrecy, ratcheting) ships.
- Peer discovery (announce, subscription filters, destination hashing, spam-resistance) ships.
- Any two ZP operators can communicate immediately upon network reachability. No external service dependency.
- Foundation-run seed peers are a bootstrap convenience, not a runtime requirement.

### II.13 The nine design principles

Structural commitments any mechanism replacement must respect. Enumerated in whitepaper §5, retained here as invariants:

1. Signing is gravity — unsigned receipts are structurally meaningless.
2. Identity is a key, not a location — cryptographic lineage, not deployment coordinates.
3. There is no center — trust state derived locally from the chain.
4. Every bit counts — no redundant fields, no duplicate data paths.
5. Store-and-forward is primary — the chain survives outages.
6. A tool is intent, crystallized — semantics in structure, not in comments.
7. Contact does not commit — reaching the world does not update the substrate.
8. One canonical path per substrate concern — no half-state from duplicate paths.
9. The system acts; the operator signs — every consequential action requires operator authority.

### II.14 Canonical substrate form

- The substrate's canonical form is a reproducibly-built operating system with operator-controlled hardware trust chain — Sovereign Form per Part XIV and SUBSTRATE-FORM-2026-07.md.
- Non-canonical forms (Appliance, Companion) are structurally recognized and permitted, and must display Form Disclosure at every operator surface. Compatibility mode without honest disclosure is not a compatibility mode.
- Layer A binaries carry the current Form as a compiled property. Attempts to run a Layer A build on a Form incompatible with its compiled Form are rejected by the substrate at boot.
- Form graduation between Companion, Appliance, and Sovereign is a chain-anchored ceremony carrying operator Genesis signature. Silent graduation is not possible.

### II.15 Substrate boundary planes

- Three Layer A tiers govern the substrate's trust boundaries: **Observation Plane** (external state → chain), **Quarantine Plane** (incoming artifacts → substrate trust), **Cognitive Input Plane** (chain → Regent's context). Each is default-restrictive, Genesis-derived, chain-anchored, structurally enforced.
- Every artifact entering the substrate's trust boundary passes through the Quarantine Plane. Default posture is deny; admission requires operator delegation ceremony per QUARANTINE-PLANE-2026-07.md.
- Observation scope is delegation-gated per OBSERVATION-PLANE-2026-07.md. Baseline is the substrate's own footprint; broader scopes require operator-signed `delegation:observe:*` receipts.
- Regent's cognitive input is composed by a signed matrix specification, not by ad-hoc accumulation. Standing corrections, precedent, and commitments occupy top-tier priority per COGNITIVE-INPUT-PLANE-2026-07.md.

### II.16 Emergency response envelope

- The substrate has a graduated emergency response mechanism — the **Circuit Breaker** — operating cross-cutting across all boundary planes and the gate per CIRCUIT-BREAKER-2026-07.md.
- Escalation is monotonic across five levels (elevated attention → rate limit → soft arrest → hard trip → substrate-wide graduated response). De-escalation is asymmetric — requires deliberate operator ceremony.
- Automatic trip on qualifying trigger (officer detection, threshold breach, observer finding) is defensible under P9 as revocation of granted authority. Automatic reset is never acceptable.
- Recovery in a chain-anchored substrate is fundamentally forward-only per BLAST-RADIUS-AND-RECOVERY-2026-07.md. Chain is truth; derived state can be recomputed from a known-good checkpoint forward. The chain preserves the full emergency record.

### II.17 Cognitive discipline sandwich

- Regent's inference is bounded by three structural components: **Cognitive Input Plane** composes her input; **Claim Verifier** performs pre-emission structural check on capability and commitment claims; **Cognitive Self-Observer** performs post-emission semantic verification against ground truth. See CLAIM-VERIFIER-2026-07.md and COGNITIVE-SELF-OBSERVER-2026-07.md.
- Verifier and Observer are complementary. Verifier catches structural mismatches at emission time (deterministic, fast, can reject). Observer catches semantic mismatches after emission (evidence-based, reports findings). Neither replaces the other.
- Metacognitive fidelity is a property of the substrate, not of the model. A substrate that verifies the model's claims against chain-anchored truth converts confabulation into detectable, correctable, chain-anchored evidence.

### II.18 Chain-anchored commitments

- Regent's promises to the operator are chain-anchored via commitment receipts (`regent:commitment:notify_on:*`, `regent:commitment:check_at:*`, `regent:commitment:promised_action:*`) per CHAIN-WATCHER-AND-COMMITMENTS-2026-07.md.
- The **chain-watcher** primitive registers pattern-matching subscriptions on the chain; when a matching receipt lands, the substrate invokes registered handlers — including spawning Regent's cycle specifically to fulfill a commitment.
- Commitments survive cognitive-cycle boots because they live on chain, not in cognitive memory. Cognitive Input Plane pulls active commitments into every cycle at top-tier priority.

### II.19 Canonical composition primitive

- The substrate has one composition primitive: WASM modules implementing declared trait interfaces, chain-anchored via canonicalization ceremony, with capability delegation Genesis-derived from the operator per EXTENSION-SURFACE-2026-07.md.
- Officers, policy modules, ontology types, ceremony flows, cognitive input sources, observation surfaces, protocol adapters, and Regent verbs are all instances of this primitive at different trust delegations. No architectural distinction between "core" and "extension."
- The only difference between an internal officer and a third-party extension is who signed it and what delegation the operator granted. Same machinery all the way down.

### II.20 Physical proprioception

- On canonical hardware (Sovereign Form Tier 1+), the substrate includes a **Hardware Self-Observer** — a dedicated MCU with independent power, independent crystal, signed firmware, and Genesis-derived signing key. Observes physical properties (rail voltage/current, thermals, clock frequencies, RF detection, tamper switches, boot timing) and emits chain-anchored `observation:hardware:*` receipts per HARDWARE-OBSERVER-2026-07.md.
- Observer cannot control the main SoC. Observes and reports only. Inverts the vendor-coprocessor trust model (Intel ME watches for Intel; ZP observer watches for operator).
- Commodity hardware without an observer subsystem (Tier 0 Pi 5) is Sovereign Form; Form Disclosure names the absence honestly.

## Part III — Axioms (Layer B canonical claims)

Operator-signed canonicalized. What the substrate declares about its own identity, its bounded operator sovereignty, its coordination model.

### III.1 The sovereign operator is the fundamental unit (Decision D)

All core substrate machinery — chain, gate, officers, Cartographer, Regent, ontology, key hierarchy — is strictly per-sovereign. Collectives are not first-class substrate entities and do not receive their own Genesis, chain, or officers. Collectives are purely compositional — patterns of coordination among sovereign operators, expressed through mandates, cross-references, commons emissions, peer discovery, and community surfaces. Organizations, businesses, and other groups exist within ZP only as voluntary coordination between sovereign individuals. Sovereignty is not delegated upward.

### III.2 Trust is anchored in verification (Decision E)

Trust in claims about the world is anchored in verification where verification is available. Reputation is a fallback for claims that cannot be locally verified (behavioral claims over time, incident claims that cannot be reproduced). Trust in persistent actors in community coordination is anchored in locally-computed reputation over chain-visible behavior. Neither anchor requires a central authority. Both are structural.

### III.3 Regent's home is the operator (Decision C)

The Regent's home is the operator, not any specific device. Regent state (identity, memory, ontology view, canonical spec) is chain-anchored and replicated across all authorized devices in the sovereign's fleet. Regent's active presence — the executing instance — is on the device the operator is currently using. Only one active instance at a time. Transitions between devices happen via chain-anchored explicit handoff. Inference compute is a resource the active Regent orchestrates from anywhere in the sovereign's fleet or from cloud under mandate; hosting Regent presence and providing compute are separate roles a device may fill either or both of.

### III.4 Officer charters

Each officer's activation model and domain-specific behavior is a canonical charter. Charters bind:

- **Steward** — chain integrity, receipt validity, ontological coherence. Event-driven on chain writes.
- **Sentinel** — security posture, threat surface, credential hygiene. Event-driven on gate events, credential changes; can elevate to preempt Regent scheduling for security-critical findings.
- **Forge** — operational state, process fleet, resource health, port coherence. Event-driven on process/port changes.
- **Cleo** — governance narration; delegation-lifecycle proposals (per Decision F). Event-driven on governance-significant events.
- **Aegis** — constitutional-trajectory monitoring. Continuous read of Cartographer ontology and other officers' findings.

Each charter references a specific canonicalized WASM module hash implementing the officer's domain logic. Charter amendment via canonicalization ceremony.

### III.5 Cartographer maintains but does not attest

The Cartographer materializes the ontology from the chain. It maintains local cache state, updates on new receipts, rebuilds from chain if state is corrupted or stale. It emits no signed chain receipts; its state changes are local events. It provides read-only ontology access to officers and Regent; write access is limited to its own materialization and to operator-signed corrections that come from outside the Cartographer itself.

### III.6 Two-layer amendment

Layer A ships in the substrate binary. Amendments to Layer A require a new substrate release through the release chain per SOFTWARE-INTEGRITY-ATTESTATION-2026-07.md — multi-party ceremony, hardware-backed keys, reproducible builds, community verification. Layer A amendments are rare and consequential.

Layer B (this document's axioms, ontology definitions, and referenced WASM modules) amendments happen via canonicalization ceremony on the operator's chain. Ceremony rigor scales with the amendment's scope per II.11. The runtime observes canonicalization receipts and adjusts within one cognitive cycle.

### III.7 Peer verification is precise

Two substrates hold "the same" behavior if they hold the same Layer A binary hash (via SOFTWARE-INTEGRITY-ATTESTATION release chain) and the same set of canonicalized Layer B artifact hashes. Peer verification of substrate equivalence is hash comparison at every layer, not semantic-equivalence argument.

### III.8 Bounded operator sovereignty

The operator has full authority over Layer B — any WASM module can be swapped, any threshold amended, any charter tuned, any coordination protocol modified via canonicalization ceremony. The operator has no authority to amend Layer A — cannot ceremony their way through a conservation law. This boundary is what protects the substrate from operator fuckery: sovereignty operates at Layer B; identity is defended at Layer A.

Attempted Layer B amendments that would violate Layer A are rejected by the runtime at parse or load time. No override flag exists.

### III.9 Human control at Genesis

Every action the substrate takes traces to threshold M-of-N humans consenting through their individual Geneses. Machine-authored actions exist within the delegation and mandate scope humans have signed. Autonomous action is per-precedent within operator-signed delegation; escalation to operator is required for novel situations.

### III.10 Trust corpus grows from precedent

The Regent's autonomous action envelope grows over time through chain-visible operator-signed precedent, not through declared configuration. Fresh substrates escalate; mature substrates handle routine autonomously; every extension of autonomous scope traces to a specific operator signature at a specific moment.

### III.11 Verification-anchored self-understanding

The substrate's declared self-understanding — its axioms, its ontology, its identity claims — is chain-anchored, operator-signed, deterministically parseable. Not the output of any inference. The Regent's interpretive observations over prose narrative are advisory, not canonical.

### III.12 Metacognition as load-bearing capability

The substrate observes its own cognitive processes across nested timescales. Metacognitive observation is what allows the substrate to detect operational drift, recalibrate its own thresholds, distinguish routine from novel, and honestly report its own state without depending on external evaluation. Reflexivity — the observer and the observed being the same system — is a structural property of the Regent's nested observer windows, the officer self-improvement loop, the model-prompt coupling awareness, the confabulation-gap detection, and the precedent-based autonomous action heuristic. Bounded to two or three levels of nesting (short window observing raw signals, medium window observing short-window aggregations, long window observing medium-window session profiles) to prevent unbounded recursion.

### III.13 Chain is truth; ontology is understanding

The chain is the substrate's source of truth. Everything else — the ontology, the officers' findings, the Regent's memory, the Cartographer's projections — is derived. If the chain says A happened at time T, then A happened at time T; nothing above the chain can override that. If the ontology says A means something different, the ontology is wrong and gets rebuilt from the chain. Inferences that contradict chain-visible facts lose to the chain by construction. This asymmetry is what makes the substrate's guarantees load-bearing rather than negotiable.

### III.14 Cartographer materializes continuously

The Cartographer runs as a background process within `zp-server`, event-driven on new chain entries with a periodic timer as fallback. It maintains a high-water mark of last-processed sequence number; on restart it replays from the mark. Full ontology rebuild from chain is always possible by discarding local cache and letting the Cartographer replay. This is the guarantee that keeps the chain as single source of truth: the ontology is a cache of understanding, disposable and re-derivable, never an independent store.

### III.15 Sovereign fleet as one coordinated substrate

The set of devices authorized by a sovereign's Genesis forms one substrate, not N substrates. State replicates across authorized devices. Officers run wherever they're authorized. Regent presence migrates via handoff. Inference compute pools across devices via rally. Chain sync keeps all devices' local mirrors converged. Peers interact with "the operator" — the mesh routes to whichever device is currently active, not to a specific device by identity.

### III.16 Precedent grows autonomous scope

The Regent's autonomous action envelope expands through chain-visible operator-signed precedent, not through declared configuration. Fresh substrates escalate all novel patterns; the operator approves or rejects; approvals become precedent receipts. Mature substrates handle routine remediation and orchestration without operator involvement because the specific pattern has been operator-signed before. Every extension of autonomous scope traces to a specific operator signature at a specific moment. Revoking a precedent (per Phase 7 of the EXECUTION-AUTHORITY-MODEL) narrows the autonomous scope back and is itself a chain event.

### III.17 Peer-to-peer messaging as constitutional capability

Any two ZP operators can communicate immediately upon network reachability, without external service, without Foundation involvement, without prior configuration. This is not a policy commitment; it is a structural capability compiled into the substrate binary (Layer A per II.12). Ripping out messaging capability would require shipping a substrate binary that isn't ZP. This axiom pins the property as canonical — any Layer B canonicalization that would degrade universal reachability is rejected.

### III.18 Delegable safety

Safety mechanisms only work long-term when they compose with delegation ceremonies that respect operator authority. Rigid safety mechanisms without proper delegation paths get bypassed, degraded, or abandoned — as evidenced by every mainstream sandboxing model (Gatekeeper → spctl disable, iOS sandbox → jailbreak, Chrome extensions → blanket permission, SELinux → permissive mode). Every structural restriction the substrate imposes must have a corresponding chain-anchored delegation path by which the operator can, deliberately and reversibly, grant admission — without disabling the restriction for anything else. Safety and sovereignty are not in tension when the mechanism is Genesis-signed delegation. This principle unifies normal delegation ceremony (deliberate admission per QUARANTINE-PLANE-2026-07.md) with emergency circuit breaker response (fast broad revocation with asymmetric reset per CIRCUIT-BREAKER-2026-07.md).

### III.19 Detectability over invulnerability

Silence is the enemy, not compromise. Compromise you can see is manageable; compromise you can't see is silent and structural. The substrate's security posture prioritizes *provable detection* over aspirational invulnerability. Every substrate boundary emits chain-anchored evidence of what crossed it and why. Every officer emits chain-anchored findings on qualifying observations. Every extension operates within delegation bounds that produce chain-anchored evidence when tested. Compromises that produce chain-anchored evidence are detectable and remediable; compromises that leave no trace are structurally impossible under this discipline.

### III.20 Forward-only recovery

Recovery in a chain-anchored substrate is fundamentally forward-only. Chain is truth; chain is append-only; the substrate does not roll back truth. What CAN be recovered is *derived state* — the Cartographer's ontology, runtime caches, computed views. Recovery means recomputing derived state from a chain-anchored checkpoint receipt forward. The chain preserves the full record of any emergency (arrest actions, refused operations, remediation activity, reset ceremony) as permanent audit trail. This inverts the traditional "rollback to before the bad thing happened, discard the record" model. Truth is preserved; convenience is not the trade. See BLAST-RADIUS-AND-RECOVERY-2026-07.md.

### III.21 Priority-weighted cognitive context

Regent's cognitive context is a priority-weighted stream, not a bucket where more information helps. What appears at the top and bottom of her context window gets weight; middle content gets attention scraps. Adding information to her context does not help if the added information gets buried behind noise. Ordering IS signal. Standing corrections, active precedent, and outstanding commitments occupy Tier 1 (top priority) of her cycle prompt per COGNITIVE-INPUT-PLANE-2026-07.md. The composition itself is chain-anchored evidence via `cognitive:input:composed` receipts. If Regent later claims not to have known something, the chain shows what she was given.

### III.22 Verify before commit

Every claim about the substrate — architectural, state, capability, precedent — passes through verification before it becomes canonical. Verification is a discrete step, not a hoped-for outcome. This principle applies uniformly: to substrate architectural claims (against KEEL and empirical program), to design elaborations (against verification evidence), to working heuristics (against N distinct instances before canonization), to current-state descriptions (against reading actual config/running process), to Regent's self-reports (against chain query for actual receipts), to fix implementations (against empirical loop confirmation), to task completions (against actual state verification). When plan and reality both exist, read the reality, don't infer from the plan. Composes with II.17 (cognitive discipline sandwich) — the Cognitive Self-Observer is the automated realization of this discipline for Regent's outputs.

### III.23 Coordination, not oversight

The substrate provides coordination primitives — specific, purposeful, narrow sharing between sovereigns whose lives include shared work. The substrate does not provide oversight primitives — categorical, ongoing, review-shaped scopes over another sovereign's life, activity, or relationship graph — even under explicit mutual grant. Surveillance shape produces known harms (coercion, jealousy amplification, control dynamics) that coordination shape does not; categorical mutual-review affordances put thumb on scale toward transparency-as-trust in a way that damages the relationships that supposedly benefit. Real trust in mature relationships often includes granted privacy — the choice not to know everything — and the substrate respects that by not making review a first-class transaction. When two operators want to share more than coordination primitives support, they do it through conversation and lived context, outside substrate mediation. Alignment incentivized, not surveilled — aligned life (where stated relationships, chain-anchored commitments, and actual behavior cohere) fits primitives naturally; misaligned life generates friction proportional to divergence, not from watching, but from the natural weight of maintaining divergent narratives across chain-anchored infrastructure. Nobody's watching. The friction is the incoherence itself. The substrate is a fitting-shape for coherent lives; everyone lives better in coherent lives, and the substrate is shaped to reward that shape without prescribing how anyone should live. Elaborated in SOVEREIGN-KINSHIP-PRIMITIVES-2026-07.md and CRISIS-RESPONSE-CEREMONY-2026-07.md; applies across every cross-sovereign primitive class.

### III.24 Aligned blindness

An aligned substrate has no business observing or retaining data classes whose holding creates only harm — either directly (breach exposes secrets no substrate should have held) or downstream (chain-anchored records used against operator's interests in circumstances the operator can't foresee). The question is not "would the operator want us to observe this?" or "could we usefully observe this?" — the question is "does an aligned substrate have any legitimate business seeing this class of data?" For some classes, the honest answer is no. Blindness is not privacy configuration layered on top of a permissive baseline; it is a moral property of what the substrate is. What the substrate structurally refuses to see is part of its alignment identity — as constitutive as what it does see and how it acts on what it sees. Four-layer refusal discipline: structural inability (baseline substrate lacks the observation mechanism — no keylogger, no full-screen capture, no clipboard monitoring, no camera-stream ingestion, no cryptographic-key observation, no intimate-content observation, no dependent-communication observation); default refusal with elevated ceremony (continuous location, individual financial transactions, medical diagnoses, mental-health state, protected-class information, legally-privileged communications — substrate can be authorized for narrow scope but never as background telemetry); scrubbing before chain-anchoring (command-line secret patterns, URL-embedded credentials, sensitive filenames, API request bodies — substrate observes surface but scrubs before storing); cognitive-layer boundary (raw sensing signals, communication bodies, credential values, detailed medical inferences — findings only reach Regent, never raw content). Operator can extend blindness for their specific concerns and can strengthen canonical classes but cannot structurally override them — alignment properties are invariant across operator preferences. Some data is toxic; the substrate holds none of it. Elaborated in SUBSTRATE-BLINDNESS-HEURISTICS-2026-07.md.

### III.25 Distributed cognition with central intent; autonomic operation; deliberate upgrades

Substrate architecture is octopus-shaped: central cognitive authority (Regent) proposes intent based on operator direction; distributed intelligence (officers, extensions, builder swarms) executes with local adaptation, coordinating with neighboring components directly rather than through central relay. Central attends to novelty and consequence; local components handle routine within pre-authorized scope. Symphony not jam band and body processes not consciousness are illuminating adjacent framings; octopus is the primary structural metaphor because it captures the distributed cognition both prior framings miss. Substrate maintains coordinated coherent behavior autonomically — routine coordination, homeostatic regulation, self-correction, immunity response, and healing all happen without operator cognitive engagement. Operator's deliberate cognitive engagement is reserved for entertaining upgrades: considering whether to change scope, adopt new discipline, extend delegation, or direct architectural evolution. Substrate self-corrects to harmony on its own; operator directs evolution. Resilience emerges from distribution — component failure is degradation, not collapse. Runaway alarms, noisy findings, and false-positive cascades are direct violations of this discipline: they force central cognitive engagement onto routine flow that should stay in local scope, polluting the intent-flow substrate depends on. Signal quality is coordination hygiene, not merely operational aesthetic. Elaborated in SUBSTRATE-COORDINATION-DISCIPLINE-2026-07.md, OFFICER-ACTION-SURFACES-2026-07.md, and AUTONOMIC-LAYER-IMPLEMENTATION-ROADMAP-2026-07.md.

## Part IV — Ontology Definitions

Formal boundaries for load-bearing terms. Each has a canonical form as a signed structured record.

### IV.1 Core substrate

- **Sovereign** — a human or an M-of-N human ceremony that controls a single Genesis. Fundamental unit of substrate authority.
- **Genesis** — the root Ed25519 seed for a sovereign. Single per sovereign. Human-controlled at ceremony time. Source of all subsequent key derivation and certification.
- **Chain** — the append-only sequence of signed hash-linked receipts on one sovereign's substrate. Structurally per-sovereign. Not shared across sovereigns. The substrate's source of truth: anything above the chain is derived and correctable against it.
- **Receipt** — the atomic chain unit. Signed, hash-linked, schema-conformant per whitepaper §4.1.
- **Gate** — the compiled Layer A code path every side-effecting action passes through. Non-bypassable.
- **Signature** — Ed25519 over the signable structure of a receipt, verifying the signing key's authorization at that moment.
- **Substrate** — the compiled ZP runtime plus its canonical spec, running on the operator's devices. What "runs ZP" refers to.
- **Ecosystem** — the set of operators running compatible ZP substrates, plus the coordination patterns among them. What "the ZP community" refers to.
- **Foundation** — one peer in the ecosystem that maintains the reference implementation, publishes canonical invariants, and runs bootstrap seed peers. Not an authority over operators; not a required intermediary; not a certification body. Retains trademark on "ZeroPoint" and defends the integrity clause per LICENSING-AND-INTEGRITY-2026-07.md.

### IV.2 Key material

- **Genesis-derived key** — Ed25519 or symmetric key material produced from Genesis via HKDF, or Ed25519 keypair produced deterministically from Genesis via chain-code derivation. Same input, same output.
- **Genesis-certified key** — locally-generated Ed25519 keypair (device or officer) whose authorization traces to a chain-anchored provisioning receipt signed by Genesis.
- **Vault** — sealed container for material persisting across sessions. Held on operator's device, unlocked by sovereignty provider (Secure Enclave, TPM, StrongBox, hardware wallet, passphrase fallback).
- **Sovereignty provider** — the hardware or ceremony mechanism protecting Genesis material. Chosen per device at Genesis ceremony.

### IV.3 Cognitive layer

- **Regent** — the operator's apex cognitive entity. One per sovereign. Home is the operator; active presence is the currently-used device; state is chain-anchored and replicated.
- **Officer** — a domain-specialized authority: Steward, Sentinel, Forge, Cleo, Aegis. Each holds a hardware-backed Genesis-certified signing key; each executes as WASM core against Layer A Officer trait interface.
- **Cartographer** — substrate infrastructure that materializes the ontology from the chain. Holds no key. Emits no signed chain receipts.
- **Ontology** — the local structured projection of the chain into typed objects and typed relationships. Rebuildable from chain. Per-sovereign.
- **Metacognition** — the substrate's reflexive observation of its own cognitive processes. Primarily embodied in the Regent's nested observer windows (short/medium/long timescales), the officer self-improvement loop, the confabulation-gap detection between fast and slow cognitive layers, the model-prompt coupling awareness, and the precedent-based autonomous action heuristic. Distinct from exocognition (officers observing external substrate state) by its reflexivity: observer and observed are the same system. Bounded to two or three levels of nesting to prevent unbounded recursion.
- **Reflexivity** — the property of a metacognitive process where observer and observed are the same entity or system. Metacognition is one form of reflexivity; other forms include the Cartographer materializing an ontology that includes receipts about the Cartographer's own operation.
- **Introspection** — narrower than metacognition; observing one's own reasoning process in a given moment (rather than over time). The Regent's confabulation-gap detection is introspective.
- **Self-awareness** — broader than metacognition; awareness of identity, values, historical patterns, and role. The Regent's memory of her own precedent chain is self-awareness.
- **Metacognitive fidelity** — how accurately self-observation matches actual cognitive state. Empirically measurable; a target for observer-window calibration.
- **Working memory (session memory)** — ephemeral state the Regent maintains for the current cognitive session. Destroyed at session end unless explicitly consolidated to long-term memory via operator-signed receipt.
- **Long-term memory (persistent memory)** — Regent state that persists across sessions. Encrypted under the operator's persistent-memory key. Consolidation from working memory happens through chain-anchored receipts that record what was learned.
- **Precedent receipt** — chain-anchored operator-signed receipt that establishes autonomous action authority for a specific (finding_type, remediation_verb, context_signature) tuple. The Regent's autonomous scope is the union of currently-active precedents.
- **Confabulation gap** — the diagnostic disagreement between the Regent's fast layer (what the current inference produces) and slow layer (what the stable user/context model predicts). Surfaced rather than suppressed; treated as information about which layer is misreading the situation.

### IV.4 Ontology objects

- **Trajectory** — a living arc of work or thinking that emerges from activity. Central primitive.
- **Decision** — a meaningful choice within a trajectory, with rationale and outcome tracking, superseded by later decisions.
- **Insight** — a key realization or observation within a trajectory, with implications and confidence.
- **Artifact** — created work (code, documents, designs, specs) linked to the trajectory and decision that produced it. Content-addressed.
- **Friction** — a blocker or recurring problem within a trajectory, with severity, occurrence count, and resolution status.

### IV.5 Authority and coordination

- **Delegation** — chain-anchored grant of scoped capability from grantor to grantee. Verified against the eight invariants. Narrows monotonically.
- **Mandate** — a specific kind of delegation with time bounds, budget caps, and specific purpose. Used for cloud escalation, research participation, cross-operator coordination.
- **Capability class** — a semantically grouped set of tools/actions (chain:read, host:execute, network:egress). Delegations are issued in class-terms, not per-tool.
- **Canonicalization ceremony** — operator-signed chain event that amends Layer B canonical spec by referencing new artifact hashes.
- **Provisioning receipt** — Genesis-signed receipt authorizing a locally-generated device or officer signing key.

### IV.6 Two-layer artifacts

- **Layer A** — the compiled substrate binary. Invariants live here. Not amendable via canonicalization.
- **Layer B** — chain-anchored operator-signed spec. WASM modules for code, structured records for data. Amendable via canonicalization ceremony.
- **WASM module** — content-addressed deterministic executable artifact loaded at runtime. Conforms to a Layer A trait interface. Sandboxed with resource metering.
- **Canonical data record** — chain-anchored operator-signed structured record parseable deterministically.
- **Composition** — the pattern where officers and other Layer B components consist of Layer A host imports + Layer B WASM core, with the host mediating capabilities.

### IV.7 Coordination primitives

- **Peer discovery** — Reticulum-compatible announce broadcast + local subscription filter. Enables any two ZP operators to find each other without central directory.
- **Mesh transport** — transport-agnostic packet-routing substrate. Works over LoRa, WiFi, TCP, serial. Ships in substrate binary.
- **Announce** — signed identity broadcast under a namespaced category. Emitting party's public key + destination hash + capability metadata.
- **Session** — time-scoped interaction with defined start and end. Attendance manifest at open time; ephemeral (content destroyed at close) or persistent (content encrypted to participants for retention) per convener choice.
- **Locked-door session** — session with membership lock, observer lock, cryptographic content lock, or invitation lock (any combination) declared at open time. Composes with non-recording attestation for strong ephemerality.
- **Commons emission** — anonymous content-addressed pattern for locally-verifiable claims. No persistent emitter identity. Verification by recipient is the trust model.
- **Security signal** — identified emission with composite trust (source rep + corroboration + officer attribution + recency). For claims that aren't locally verifiable.
- **Community surface** — bounded or portable channel where sovereign operators gather. Reputation of participants locally computed per operator.
- **Bounded space** — space where operators participate as space-scoped identities (derived per DISTRIBUTED-KNOWLEDGE-COMMONS pattern-sharing key ceremony). Reputation stays within the space; external observers see only the space-specific key.
- **Portable space** — space where operators participate as their persistent identity. Reputation earned carries forward into other portable contexts.
- **Collective** — a coordination pattern among sovereign operators expressed through mutual mandate and cross-reference. Not a substrate entity.

### IV.8 Multi-device operation

- **Sovereign fleet** — the set of devices authorized by a sovereign's Genesis to participate in that sovereign's substrate operation.
- **Device role** — active-Regent-host, inference-host (rally target), sensor-gateway, view-only. A device may hold multiple roles.
- **Active presence** — the currently-executing Regent instance. Exactly one at a time per sovereign. Chain-anchored via a presence receipt.
- **Handoff** — chain-anchored explicit transition of active presence between devices. Includes state package + signature from source device + acceptance signature from destination.
- **Rally** — mandate-scoped invocation of inference or other compute from non-Regent-hosting devices in the sovereign's fleet.
- **Genesis ceremony** — the initial substrate boot ceremony where the sovereign's Genesis keypair is generated, the first device is provisioned, sovereignty provider is bound, and the operator's chain is initialized with a signed Genesis receipt. Atomic and irreversible.
- **Provisioning ceremony** — subsequent chain-anchored ceremony where a new device or officer's locally-generated key is Genesis-certified via signed provisioning receipt. Composable across ceremonies as the fleet grows.
- **Canonicalization ceremony** — see IV.5. Chain-anchored ceremony that amends Layer B canonical spec.
- **Constitutional amendment ceremony** — the Tier 3 canonicalization ceremony for significant Layer B changes: multi-signature from all provisioned sovereign devices, 14-day cooling period, active final confirmation.

### IV.9 Trust primitives

- **Verification** — direct evaluation of a claim against locally-available evidence.
- **Reputation** — chain-visible observed behavior over time, locally computed by each operator's substrate against their own trust graph. Not centrally maintained.
- **Composite trust** — combined signal from source reputation, corroboration by other sources, officer attribution, recency, weighted per receiver's own configuration.
- **Corroboration** — independent sources reporting compatible claims. Content-addressing makes corroboration natural in anonymous emissions.
- **Attestation** — chain-anchored signed claim about substrate behavior (runtime, build, non-recording, DP-budget-accounting). Reputation stake makes false attestations costly.
- **Finding** — chain-anchored signed report from an officer about substrate state observed within that officer's domain (chain integrity, security posture, operational health, governance narrative, constitutional-trajectory drift). Emitted by officer's WASM core, signed by officer's hardware-backed key.
- **Claim** — the general term for any assertion the substrate makes about the world, itself, or another party. Attestations and findings are specific kinds of claims that meet particular trust criteria.
- **Verification-as-trust-model** — the trust posture where recipients evaluate claims locally rather than trusting emitter identity. Used by gossip and commons emissions.

### V.4 Handoff protocol

```
// Handoff receipt chain:
//   1. Source device emits regent:handoff:requested { target_device, snapshot_hash }
//   2. Target device emits regent:handoff:accepted { source_device, snapshot_hash }
//   3. Source device signs regent:handoff:complete { target_device, snapshot_hash, closed_at }
//   4. Peers observe the complete receipt and route future messages to target_device.
//
// Between (1) and (3), the substrate is in transition:
//   - Source device is no longer accepting operator input.
//   - Target device is not yet accepting operator input.
//   - Autonomous work in progress on source pauses at natural checkpoint boundaries.
//   - Session state is packaged, transferred, verified, mounted.
//
// If transition fails (target rejects, timeout, hash mismatch):
//   - Source device emits regent:handoff:aborted { reason }
//   - Source device resumes active presence.
//   - Operator sees failure surfaced through cockpit.
//
// If source device dies mid-transition (heartbeat lost):
//   - Any authorized device can emit regent:handoff:recovery { source_device, last_seen }
//   - Substrate accepts if source's presence receipt is stale beyond recovery threshold.
//   - Operator authenticates on new device; new device claims active presence.
```

### V.5 Rally invocation

```
// Rally receipt chain:
//   1. Regent's active device emits regent:rally:requested { target_device, task, model, budget }
//   2. Target device emits regent:rally:accepted { task_id } if it has the resources and mandate authorizes
//   3. Target device emits regent:rally:result { task_id, output_hash, tokens_consumed, wall_time }
//   4. Active device emits regent:rally:integrated { task_id } after using the result
//
// Mandate scope enforced by host at both endpoints:
//   - Requester must hold a rally mandate authorizing target and model
//   - Target must recognize the requester's mandate (via chain-verifiable delegation)
//   - Budget consumed from mandate on completion; exhaustion causes future requests to fail
//
// Failure modes:
//   - Target unreachable: regent:rally:timeout, active device falls back to next preferred target
//   - Target rejects: regent:rally:rejected, reason coded
//   - Result invalid (schema, size): regent:rally:invalid_result
```

### V.6 Chain replication under mandate

```
// Cross-operator chain sharing (per COLLECTIVE-ADOPTION coordination pattern):
//   1. Operator A grants operator B a chain-replication mandate scoped to specific categories
//   2. B's substrate fetches A's chain segment (via mesh) under the mandate
//   3. B's Cartographer materializes A's segment as ontology fragments tagged with source
//   4. B's officers can attest to A's chain segment integrity but cannot modify it
//   5. Revocation: A emits mandate:revoked, B stops fetching new receipts, retains what was shared
```

Host mediates all cross-operator replication. WASM modules cannot directly share chain data without host-validated mandate.

## Part VI — Canonicalization Ceremony

Structure of amendments to Layer B canonical spec.

### VI.1 Ceremony receipt structure

- **type**: `canonicalization`
- **id**: content hash of the receipt
- **spec_layer**: `axiom` | `ontology_definition` | `officer_charter` | `wasm_module` | `other_spec_field`
- **spec_id**: canonical identifier of the specific artifact being amended
- **artifact_hash**: Blake3 hash of the new canonical artifact
- **supersedes**: content hash of the prior canonical form, if this amends rather than adds
- **rationale**: hash of the human-readable rationale (Markdown source), if any
- **tier**: 1 | 2 | 3
- **operator_signatures**: array of Ed25519 signatures (per Tier requirements)
- **cooling_period_start**: timestamp if Tier 3 (14-day cooling required before effective)
- **final_confirmation**: signature after cooling period if Tier 3
- **standard receipt fields**: pr, ts, etc.

### VI.2 Runtime observation

The substrate maintains a subscription to canonicalization receipts. On observing a valid new canonicalization:

1. Verify operator signature(s) against operator's chain signing key(s) authorized at receipt timestamp.
2. If Tier 3, verify cooling period elapsed and final_confirmation present.
3. Fetch the referenced artifact by hash (via peer-replication if needed).
4. Verify artifact content matches artifact_hash.
5. Verify artifact conforms to Layer A constraints for its spec_layer (WASM traits, structured-record schemas, etc.).
6. If any check fails, reject the amendment with a chain-anchored rejection receipt.
7. If all checks pass, load the new artifact and adjust behavior within one cognitive cycle.

### VI.3 Tier gate rejection

Amendments crossing tier boundaries are rejected structurally. An amendment that names Tier 1 but would change officer identity, for example, gets rejected at parse — the runtime checks the actual change scope against the declared tier and rejects mismatches.

Amendments that would violate Layer A invariants get rejected regardless of tier. There is no Tier 4 for Layer A amendments in this system; those go through substrate binary release.

### VI.4 Rejection receipts

When the runtime rejects a canonicalization amendment (invalid signature, tier mismatch, Layer A violation, artifact hash mismatch, WASM trait non-conformance), it emits a chain-anchored rejection receipt:

```
type: canonicalization_rejected
canonicalization_receipt_id: <hash of the rejected amendment>
rejection_reason: enum {
  InvalidSignature,
  TierMismatch,
  LayerAViolation,
  ArtifactHashMismatch,
  TraitNonConformance,
  CoolingPeriodNotElapsed,
  MissingFinalConfirmation,
  ArtifactUnfetchable,
  OtherStructural,
}
rejection_detail: string  // human-readable specifics
ts: <timestamp>
sg: <substrate binary's release-signing key over the rejection>
```

The rejection is signed by the substrate itself (via the release chain's authority), not by the operator. This makes rejections auditable and prevents silent failures: any amendment attempt produces either an applied receipt or a rejected receipt on chain.

### VI.5 Bundled amendments

Multiple related artifacts can be canonicalized in one ceremony. A canonicalization receipt may reference an array of artifacts:

```
artifacts: [
  { spec_layer: officer_charter, spec_id: aegis-charter, artifact_hash: <hash> },
  { spec_layer: wasm_module, spec_id: aegis-impl, artifact_hash: <hash> },
  { spec_layer: ontology_definition, spec_id: trajectory-drift-signal, artifact_hash: <hash> },
]
```

Bundled amendments are atomic — either all artifacts load successfully and the amendment applies, or the runtime rejects the entire bundle and none apply. Prevents partial-state where charter references a WASM module that doesn't exist yet.

### VI.6 Rollback

When an amendment has landed but produces broken behavior (officer crashes, WASM module fails runtime checks after initial load, unexpected empirical drift), the operator can emit a rollback canonicalization receipt:

```
type: canonicalization
spec_layer: <same as the amendment being rolled back>
spec_id: <same>
artifact_hash: <hash of the prior canonical form>
supersedes: <hash of the amendment being rolled back>
rollback_reason: string
```

Rollback is itself a canonicalization ceremony subject to tier rigor. Tier 3 amendments require Tier 3 rollback ceremony. The chain shows both the amendment and the rollback, so the history of what was tried is preserved.

### VI.7 Amendment sequencing during transition

Between amendment observation and application, the substrate is in transition. During this window:

- If the amendment is a WASM module swap, the outgoing module continues running until the new module has passed all load-time checks. Switchover is atomic at the runtime's next cognitive cycle boundary.
- If the amendment is a canonical data record change, the runtime maintains both old and new records until the switchover moment, then commits atomically.
- If the amendment is Tier 3 mid-cooling-period, the substrate continues operating under pre-amendment rules; the amendment is only visible on chain, not effective.
- Concurrent amendments to the same spec_id are serialized by chain ordering — the later canonicalization receipt supersedes the earlier if both are valid.

## Part VII — Peer-Verification Contract

How two substrates verify they're running "the same thing."

### VII.1 Layer A verification

- Each substrate's binary hash is chain-anchored via a release receipt signed by the release-signing authority (Foundation or community fork chain).
- Peer verification of Layer A equivalence: compare binary hashes; walk the release chain to a mutually-trusted release-signing key.

### VII.2 Layer B verification

- Each substrate's canonical spec is a set of canonicalization receipts anchored on that operator's chain.
- Peer verification of Layer B equivalence: compare the set of currently-canonical artifact hashes for the roles being verified.
- Full behavioral equivalence: same Layer A binary + same Layer B artifact hashes.

### VII.3 Behavioral verification

- Officer findings, Regent actions, Cartographer projections are all deterministic given (Layer A + Layer B + same inputs).
- Peer replay: given a peer's chain segment (under mandate-scoped disclosure), a verifier can replay the same officer sweeps and expect identical findings.
- Discrepancies indicate either (a) different Layer A or Layer B, or (b) tampered chain, or (c) bug in the substrate.

## Part VIII — Bounded Operator Sovereignty

What operators can and can't amend.

### VIII.1 Full operator authority (Layer B)

- Officer charters (activation cadence, thresholds, signal inputs, WASM implementation).
- Cartographer projection rules and thresholds.

- Presentation-layer defaults.

### VIII.2 No operator authority (Layer A)

- Constitutional rules (HarmPrincipleRule, SovereigntyRule).
- Delegation narrowing invariants.
- Chain integrity mechanisms.
- Cryptographic primitives.
- Gate atomicity.
- Officer trait interfaces (as trait definitions, not as implementations).
- Cartographer trait interface.
- WASM sandbox capability surface.
- Canonicalization ceremony structure itself.
- The two-layer separation.

### VIII.3 Runtime enforcement

The substrate refuses to run against a canonical spec that would violate Layer A. This refusal is structural — no override flag, no operator ceremony that bypasses. The operator can amend anything in Layer B; the substrate defends its own identity at Layer A regardless.

## Part XI — Genesis Ceremony

The initial substrate boot ceremony. The moment a sovereign comes into existence within ZP.

### XI.1 Sovereignty provider selection

Before Genesis material is generated, the operator selects the sovereignty provider that will protect it:

- **Secure Enclave (macOS/iOS)** — Touch ID or Face ID unlocks a key that seals Genesis material.
- **StrongBox (Android)** — biometric or PIN unlocks a key that seals Genesis material.
- **TPM (Windows/Linux)** — platform authentication seals Genesis material.
- **Hardware wallet (YubiKey, Trezor, Ledger, dedicated ZP token)** — external hardware holds a wrapping key; touch confirms unlock.
- **Passphrase (fallback)** — Argon2id-derived key from a passphrase. Weakest option; last resort.
- **M-of-N sovereign quorum** — Shamir-shared Genesis, requiring K of N hardware roots to unlock. For collectives-of-humans that will operate as a single sovereign, or for solo operators requiring multi-device defense.

The provider choice binds at ceremony time. Migration between providers is a subsequent chain-anchored ceremony.

### XI.2 Genesis keypair generation

Ed25519 keypair generated inside the sovereignty provider using its hardware entropy source. For hardware-wallet or Secure Enclave: Genesis private material never leaves secure hardware. For passphrase fallback: material is deterministically derived from passphrase + salt.

For M-of-N quorum: initial ceremony generates the master Genesis seed, splits it via Shamir into K shares, distributes shares to hardware roots. Master seed is destroyed after split; only shares survive. Signing requires K shares to reconstruct.

### XI.3 First device provisioning

The device on which Genesis was performed is implicitly provisioned as a full-signing device — no separate provisioning receipt needed since Genesis itself was performed there. This device holds:

- Genesis sealed by sovereignty provider
- Provisional operator identity (public key fingerprint displayed for verification)
- Empty chain, ready for first receipt
- Regent skeleton (pre-Genesis mode, no persistent memory, just enough to walk ceremony)

### XI.4 Chain initialization

The first chain receipt is Genesis itself:

```
type: genesis
id: <blake3 hash of the receipt>
rt: genesis
st: success
tg: A  // highest trust grade
ch: <hash of Genesis public key and ceremony parameters>
ts: <ceremony timestamp>
pr: null  // no predecessor
pd: allow
ra: "Genesis ceremony completed"
sg: <self-signature by Genesis key>
ex: {
  sovereignty_provider: <provider identifier>,
  provider_fingerprint: <provider-specific identifier>,
  ceremony_type: single | quorum,
  quorum_config: <M-of-N params if quorum, else null>,
  substrate_version: <Layer A binary hash>,
}
```

Genesis is self-signed. Every subsequent receipt traces back through pr linkage to Genesis.

### XI.5 First mandate

The Regent needs scoped authority to be useful. The operator issues the first mandate immediately after Genesis:

```
type: delegation
grantor: <Genesis>
grantee: regent
scope: {
  chain_read: full,
  chain_write: through_gate,
  officer_findings: read,
  inference_local: allowed,
  proposals_to_operator: allowed,
  cloud_inference: null,   // not initially granted
  external_communication: null,  // not initially granted
}
depth: 0
expires: null  // no time bound at first
sg: <Genesis signature>
```

This scope is the working baseline. Additional capabilities are granted individually as the operator engages with them.

### XI.6 Initial backup posture

At Genesis, the operator sees a seed phrase (BIP-39 or SLIP-39 format per Layer A commitment) once. The Regent verifies the operator has recorded it (by asking them to confirm, not by asking them to re-enter). This is the minimum viable initial backup.

Additional backup mechanisms (peer chain replication, hardware wallet backup, M-of-N Shamir if not already used at Genesis) are deferred with a light note — the seed phrase alone is not the recommended final posture but is the ceremony floor.

### XI.7 Ceremony atomicity

Genesis is atomic and irreversible. If ceremony fails mid-flow (device dies, sovereignty provider errors, operator cancels), any partial state is discarded. On next launch, ceremony restarts from the beginning. There is no half-Genesis state.

Post-ceremony, the operator's substrate is fully operational — Genesis exists on chain, first mandate is signed, Regent is authorized to help, and the operator can proceed with any subsequent workflow.

## Part XII — Release Chain Composition

How Layer A substrate binaries move from source to adopted release.

### XII.1 Release-signing key hierarchy

The Foundation (or any other release-signing authority) maintains a release-signing key hierarchy:

- Release-signing root key — Genesis-derived from the Foundation's Genesis. Long-lived, hardware-backed, geographically distributed for M-of-N ceremony.
- Release-signing operational keys — issued by the root for specific release-signing operations, rotated regularly, chain-anchored provisioning receipts.

Communities that maintain their own forks have their own release chains under their own release-signing keys.

### XII.2 Release receipt structure

Each released substrate binary is chain-anchored via a release receipt on the release-signing authority's chain:

```
type: release
build_hash: <blake3 of the built binary>
source_hash: <hash of the source tree commit>
build_environment: {
  compiler_version: <string>,
  dependency_hashes: <map>,
  target_platform: <string>,
  reproducibility_attestation: <hash of ceremony record>,
}
declared_capabilities: <machine-readable declaration of what this build does>
supersedes: <hash of prior release receipt>
signers: <array of release-signing key fingerprints>
signatures: <threshold signatures>
release_notes_hash: <hash of human-readable release notes>
```

The release receipt is signed by threshold M-of-N release-signing keys. Any operator can verify a substrate binary matches a released receipt by hashing the binary and checking against the chain.

### XII.3 Reproducible builds

Layer A commitment: substrate binaries are reproducible. Anyone with the source can build and verify the hash matches the release receipt. Requires:

- Deterministic build tooling
- Fixed dependency versions with cryptographic hashes
- Time-independent build outputs (no embedded timestamps)
- Fixed target platform fingerprints

Reproducibility eliminates the trust dependency on any single build-signing party. Any observer can verify.

### XII.4 Community-fork release chains

Any operator or community can maintain their own release chain by:

1. Generating a Foundation-independent release-signing root key from their own Genesis.
2. Producing their own release receipts under their own signing.
3. Publishing their release chain via chain announces or their community's discovery surface.

Communities decide which release chains they accept for participation. A fork that preserves the invariants (per SUPERSESSION-FRAMEWORK) is a legitimate ZP; a fork that violates them is not (per LICENSING-AND-INTEGRITY chain-invariant rejection).

### XII.5 Release supersession

New releases supersede prior via the `supersedes` field. Operators observe new release receipts via subscription; the Regent surfaces the amendment to the operator with declared changes. Adoption is per-operator — the operator chooses whether to update. Old release binaries continue running until the operator canonicalizes the new binary.

### XII.6 Release-signing key rotation

Rotation of a release-signing key is itself a chain-anchored ceremony, dual-signed by the old key and the new key, with references to the M-of-N ceremony that authorized the rotation. Operators observing the transition update their trust anchors after verifying both signatures and the ceremony record.

## Part XIII — Boot Sequence

The substrate runtime lifecycle. What happens when the substrate starts, when it observes amendments, when it recovers from failure, when it shuts down.

### XIII.1 Cold boot (fresh install)

First time the substrate runs after installation:

1. Substrate binary launches; verifies its own hash against a Layer A embedded release-signing key.
2. Detects that no Genesis exists on this device.
3. Enters Genesis ceremony mode per Part XI.
4. Operator completes Genesis; substrate transitions to warm-boot state.

### XIII.2 Warm boot (existing install)

Subsequent starts after Genesis exists:

1. Substrate binary launches; verifies its own hash against embedded release-signing key.
2. Loads Genesis material from sovereignty provider (requires operator authentication).
3. Loads current canonical spec (Layer B artifacts referenced by the most-recent canonicalization receipts on chain).
4. Verifies WASM modules conform to Layer A trait interfaces; halts with error if any violate.
5. Initializes officer WASM sandboxes with charter configs.
6. Initializes Cartographer WASM sandbox; Cartographer begins materializing from high-water mark (or full chain replay if state is missing).
7. Initializes Regent WASM sandbox; Regent loads persistent memory from vault, resumes any in-flight WorkArc from checkpoint.
8. If this device was previously the active-presence host and no handoff completed since shutdown, Regent resumes active presence. If handoff occurred to another device, Regent boots in passive mode (observing but not acting externally).
9. Peer discovery announces resume; officers begin their event-driven activation cycles; Cartographer's high-water mark advances as new chain entries land.

### XIII.3 Canonicalization observation

When a new canonicalization receipt lands on the operator's chain:

1. Substrate's chain-watcher observes the receipt.
2. Runtime verifies signature and tier per Part VI.
3. If Tier 1: fetch new artifacts by hash, verify, load atomically at next cognitive cycle boundary.
4. If Tier 2: same as Tier 1.
5. If Tier 3: begin cooling period; substrate continues under pre-amendment rules; wait for final confirmation.
6. If any check fails: emit rejection receipt per VI.4; substrate continues under pre-amendment rules.
7. Applied amendment is chain-visible; peers observe and can verify their peer has adopted the new spec.

### XIII.4 Handoff acceptance

When a `regent:handoff:requested` receipt targets this device:

1. Device is authorized (per V.4).
2. Fetch snapshot from source device via mesh, verify snapshot hash matches receipt.
3. Load snapshot into local Regent state.
4. Emit `regent:handoff:accepted`.
5. Wait for source device's `regent:handoff:complete` receipt.
6. Assume active-presence role; begin accepting operator input.
7. Peers observe the handoff and route future messages to this device.

### XIII.5 Failure recovery

**Local process crash**: substrate is designed to be crash-safe. On restart, resume from chain state and vault; Cartographer replays from high-water mark; Regent resumes any WorkArc from checkpoint. No state loss from single-process crash.

**Active device fails mid-work**: another authorized device observes source device's presence receipt has become stale beyond recovery threshold. Any authorized device can emit `regent:handoff:recovery` claiming presence. Operator authenticates on the recovery device; new device becomes active. In-flight WorkArc resumes from last chain-anchored checkpoint.

**Chain corruption**: if local audit.db is corrupted, substrate reconstructs from peer-replicated chain segments (per XIII.3 replication mandates). If no peer copies exist, substrate cannot recover — this is the failure mode BACKUP-AND-RECOVERY-LANDSCAPE addresses.

**Canonical spec unfetchable**: if an amendment references artifacts the substrate cannot fetch (peer unavailability, hash mismatch), the amendment does not apply; substrate continues under prior canonical spec; emits `canonicalization_rejected` per VI.4. Operator can retry later or supersede the failed amendment.

### XIII.6 Shutdown

Clean shutdown sequence:

1. Regent completes current cognitive cycle.
2. In-flight WorkArc emits final checkpoint receipt.
3. Officers complete any in-progress sweeps; findings emit as chain receipts.
4. Cartographer completes current ontology update batch; high-water mark persisted.
5. Presence receipt marked as suspended (not surrendered — device retains active presence for handoff resumption on next warm boot).
6. Vault sealed by sovereignty provider.
7. Substrate process exits.

Unclean shutdown (crash, force-kill, power loss): the substrate on next warm boot detects the abnormal exit via unwritten shutdown-completion receipt, resumes from last consistent state, and proceeds with normal recovery.

## Part XIV — Substrate Realization

The substrate's canonical form is not an install on someone else's operating system. It is a reproducibly-built OS with operator-controlled hardware trust chain. Everything else is a bridge or a compatibility mode, honestly labeled.

Full technical specification lives in `docs/design/SUBSTRATE-FORM-2026-07.md`. This part captures the invariants.

### XIV.1 Three Forms

The substrate exists in exactly three Forms, each with a defined trust-chain reach, observation surface, and operator commitment.

- **Sovereign Form** — canonical. NixOS-based, reproducibly built, measured boot with operator-enrolled keys, sealed FDE bound to boot state, Genesis on hardware token. Trust chain from firmware to substrate. Observation surface: full.
- **Appliance Form** — bridge. Same substrate stack as Sovereign Form on dedicated hardware alongside operator's daily driver. Sovereign compute on the appliance; daily driver is a delegated client via Genesis-signed pairing. Trust chain: full within appliance boundary.
- **Companion Form** — compatibility. Installs on operator's existing OS. Runs within vendor permissions. Trust root is the vendor, not the operator. Observation surface: whatever the vendor permits. Explicitly labeled.

Additional Forms are not introduced by casual convention. New Forms require KEEL amendment.

### XIV.2 Canonical form is Sovereign

The canonical form the substrate declares as its own truth is Sovereign Form. Appliance Form is the pragmatic near-term deliverable. Companion Form is on-ramp and hybrid workflow. The three Forms coexist indefinitely; canonical Form is not a deprecation deadline for the others.

### XIV.3 Form Disclosure (invariant)

Every operator surface on a non-canonical Form must display Form Disclosure prominently and directly. Not buried, not hedged.

- **Companion Form Disclosure**: "You are running Companion Form. Your operating system vendor controls the trust root of this device. The substrate defends your authority within the constraints your vendor permits, but cannot defend it against your vendor. To reach full sovereignty, graduate to Appliance or Sovereign Form."
- **Appliance Form Disclosure**: "You are running Appliance Form. Sovereign compute runs on the appliance. Local state on this device remains in your vendor's permitted scope until synced to the appliance."
- **Sovereign Form Disclosure**: silence. The canonical form does not need to explain itself.

Form Disclosure is Layer A structural. Substrate builds that omit Form Disclosure on non-canonical Forms fail Layer A conformance verification.

### XIV.4 Sovereign Form trust chain

The full trust chain from firmware to substrate userland, structural:

- Firmware / UEFI with operator-enrolled Secure Boot keys.
- Bootloader (systemd-boot) with UKI signed by operator's key.
- Kernel + initramfs bundled and signed as one artifact.
- Root filesystem: LUKS2 encryption, key sealed to TPM 2.0 with PCR policy covering firmware and boot chain.
- NixOS userland verified via measured boot; system generation identity chain-anchored via boot receipt.
- Substrate services boot from verified userland with awareness of their measured-boot lineage.

### XIV.5 Hardware Genesis (Sovereign and Appliance Forms)

The operator's Genesis lives on a hardware token — YubiKey, Nitrokey, or Trezor. The substrate never holds raw Genesis material. Every operator action requiring sovereign authority — mandate issuance, delegation grant, artifact signing, Form graduation — triggers physical interaction with the token.

Loss of the token is loss of sovereignty; recovery is via M-of-N quorum of pre-registered recovery tokens per Decision A and the quorum-sovereignty design (design in progress).

### XIV.6 Reproducible artifact chain (Sovereign and Appliance Forms)

Every deployed substrate runtime traces to a signed artifact:

- Source pin: specific Nix flake commit, signed by substrate release key (Genesis-certified).
- Build product: `nixos-rebuild build` output, bit-identical from source pin.
- Boot receipt: on boot, running system emits `boot:generation` citing (source pin, build hash, PCR values), chain-anchored.
- Configuration receipt: any operator configuration change emits `config:apply` with diff and resulting expression hash, chain-anchored.

The KEEL's canonicalization principle extends to the operating system itself. What is running is provable; how it got there is provable; who authorized each transition is provable.

### XIV.7 Form is orthogonal to compute capacity

Substrate Form governs the trust chain — firmware, boot, substrate. Compute capacity governs what cognitive work can be sourced locally. These are independent axes. A Sovereign-Form device with low local inference capacity is still fully sovereign; its Regent sources cognition via one of three inference sources:

- **Local** — on the device the Regent is presently active on.
- **Rallied** — on another authorized device in the sovereign's fleet, per Decision C.
- **Cloud** — on external provider under signed CloudMandate with hard token and cost caps.

The practical floor for local inference at various model tiers is empirically unknown as of 2026-07 and is a phase of the empirical program. No Form is gated by local inference capacity. A sovereign can adopt any Form on any spec-compliant hardware and source cognition wherever they can afford or reach.

### XIV.8 Form graduation

Movement between Forms is a chain-anchored ceremony. Operator Genesis signature required. Chain state replicates across Forms per Peer-Verification Contract (Part VII).

Legal graduation paths: Companion → Appliance, Appliance → Sovereign, Companion → Sovereign (direct). Reverse graduation (Sovereign → Appliance, Appliance → Companion) is legal but degrades sovereignty reach and is explicitly acknowledged as such at ceremony time.

### XIV.9 Form composes with everything else

- **Officers** query the ontology; each Form determines the reachable observation set.
- **Observation plane** (per OBSERVATION-PLANE-2026-07.md) has Form-appropriate Layer A primitives — Sovereign and Appliance get Linux primitives (kqueue-equivalent, eBPF, sysctl, procfs); Companion gets whatever the host OS exposes.
- **Empirical program** adds Form-scoped investigations (graduation UX, chain replication under adversarial conditions, measured-boot verifiability, reproducible-build determinism, observation-surface reach).
- **Regent** sees Form as first-class cognitive context. Harmony decisions vary by Form. Regent's tool set is Form-aware; some tools are gated to Sovereign or Appliance because their authority requires reach Companion cannot grant.

Regent persona is Form-invariant. Regent's reach is Form-dependent.
